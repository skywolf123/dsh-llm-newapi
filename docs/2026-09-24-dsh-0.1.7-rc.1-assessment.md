# dsh 0.1.7-rc.1 适配评估（本分支）

> 本文记录 2026-09-24 对 dsh `0.1.7-rc.1` 的接缝核对与本次改动范围。仓库基线是上游 `v0.8.6-rc.3`（commit `713e3bd`）。上一轮（0.1.5）的记录见 [0.1.5-rc.1 适配评估](2026-09-10-dsh-0.1.5-rc.1-assessment.md)，那是历史快照，不是现行兼容说明。

## 结论

0.1.7 的接缝变更使得插件**无法同时支持 0.1.5 与 0.1.7**：设置段接缝被整体替换。本次选择只支持 0.1.7 线，`0.1.5` 及更早的宿主由入口版本 guard 明确拒绝并给出升级命令。

**版本号不在本分支改动**：`package.json` 保持 `0.8.6-rc.3`。本仓库是 `wenzetan/dsh-llm-newapi` 的 fork，适配本身是要向源项目提交 PR 的内容；包版本与 RC 标签由源项目维护者在合并后统一决定。每个 PR 都 bump `package.json` 会让上游在同一版本号下收到两个内容不同的树。

CI 的固定宿主同步抬到了 `0.1.7-rc.1`：`.github/workflows/ci.yml` 里 plugin-check 借用接缝符号的全局安装与 boot 任务的宿主安装都改成 `@deepseek-ai/dsh@0.1.7-rc.1`，boot 任务里两处提及旧宿主版本的注释一并更新（其中一处写的是 0.1.2，属历史遗留）。boot 的断言逻辑（token→cookie、HTTP 200、boot 图、RPC 信封）在新宿主上没有需要改动的地方。

## 0.1.7 相对 0.1.5 的接缝变更

### 设置段：`installSection` 被删除

| 0.1.5 | 0.1.7 |
| --- | --- |
| `ctx.settings.installSection(ns, Schema, defaults, { validate, setSource, onChange })` | 无此方法。`SettingsForms` 遍历 `configEditor.configuration()`，把每个条目的 `fiber.runtime.Config` 投影成表单 |
| 命名空间是插件自选的字符串（`llm-newapi`） | 命名空间是 profile 条目 id（`ctx.fiber.entry?.options.id`） |
| 插件通过 `setSource` 回调拿到当前配置 | 插件直接持有 `Config` 输出对象；`.volatile()` 字段是 `Volatile<T>` 引用，Loader 原地提交新值 |
| 写入时的校验走 `validate` 回调 | 写入时跑 `internal/config` waterfall；插件在这里重新校验候选值 |
| 配置热更新的通知是 `onChange` | 只改 volatile 字段时 Loader 发 `loader/volatile-update`（带变更路径），不重挂插件 |

本插件的迁移：

- `Config` 的每个可编辑字段加 `.volatile()`；`Config` 的接口类型相应变成 `Volatile<T>`，新增 `Options` 类型与 `plainOptions()` 解引用帮助函数。
- 删除 `ctx.settings.installSection(...)`，改为 `ctx.inject(['settings'], child => child.effect(() => child.settings.configure({ auto: false }, ctx.fiber)))`，表示「本插件自带设置页，不要自动生成重复表单」。
- `resolveAdapterOptions(config, env)` 改为接收解引用后的 `Options`；`options()` 每次调用 `plainOptions(config)`，因此请求间看到的是引用里的最新值。
- 校验从 `validate` 回调搬到 `ctx.on('internal/config', ...)`：只处理 `this === ctx.fiber`（即本条目自身）的候选值，抛错即拒绝写入。这与上游 `llm-pi-ai` 的 `assertServiceable` 挂钩点相同。
- 新增 `ctx.on('loader/volatile-update', ...)`：重试策略是注册时捕获的唯一事实，变化时用 `registration.replace` 原地重绑。
- 设置命名空间改为 `ctx.fiber.entry?.options.id ?? 'llm-newapi'`，并同时用在 `registerConfigurableProviders` 与 `registerModelDiscovery` 上。

浏览器半边相应改动：设置页不再假设命名空间是 `llm-newapi`，而是先从 `remote.llm.listConfigurableProviders()` 读回本路由的 `settingsNs`，再用它做 describe / mutate / discoverModels。条目被重命名时页面照常工作。

### 消息词表：工具结果升为一等消息，新增 developer 角色

| 0.1.5 | 0.1.7 |
| --- | --- |
| 工具结果是 `content` 里的 `tool-result` 块 | 工具结果是独立的 `role: 'tool'` 消息，带 `toolCallId` 字段；`ContentBlockMap` 里没有 `tool-result` |
| `Message` 只有 system/user/assistant | 新增 `DeveloperMessage`（`role: 'developer'`），以及 `tool-addition` / `tool-removal` 内容块，供 Session V4 持久化动态工具增删 |
| `GenerateOptions.messages: Message[]` | `messages: RequestMessage[]`，多出一个无 id/source 的 `RequestUserInput` |
| `ToolSchema` 只有 name/description/parameters | 新增 `deferLoading?: true` |

`serialize.ts` 的相应改动：

- `serializeMessages` 接收 `readonly RequestMessage[]`，按 `role` 分派；`role: 'tool'` 直接读 `message.toolCallId`。
- `role: 'developer'`、`tool-addition` / `tool-removal` 块、`deferLoading` 一律抛 `UNSUPPORTED_CONTENT`。这三者上游自己标注为「为 V4 预留，生产者与消费者一起落地前 provider 与 UI 都拒绝」，`llm-deepseek` 与 `llm-pi-ai` 的实现也是拒绝。静默丢弃会让模型看到的工具集与 harness 的认知不一致。
- `content` 参数改为 `readonly ContentBlock[]`（0.1.7 起消息内容声明为只读）。

### `dsh-llm` 导出面：4 增 2 减

| 新增 | 移除 |
| --- | --- |
| `IMAGE_OFFLOAD_REQUIRED_CODE` | `offloadRequestImagesWithPolicy` |
| `createDeveloperMessage` | `offloadedImagePrefixCount` |
| `projectOffloadedImages` | |
| `requiredImageOffload` | |

插件只使用两条线共有的符号（`assertUsableApiKey`、`LlmError`、`resolveRetryPolicy`、`RetryPolicySchema`、`contentHasImage`、`EMPTY_RESPONSE_CODE`、`attributionHeaders` 等），因此 `lib/index.js` 的静态导入在 0.1.5 宿主上仍能完成 ESM 链接，版本 guard 才有机会输出友好提示。`test/host-compat.mjs` 的 Block E 继续守护这一点，被拒绝的快照换成 `dsh-llm-0.1.5.exports.json`。

### 连接与 RPC：形状不变，原因相同

`connection.rpc.handle()` 在 0.1.7 上依然不可用，原因与 0.1.5 完全一致：`rpc` getter 捕获服务自身的 `ctx`，该上下文没有注入 `webServer`，`owner.webServer.register(route)` 抛 cordis 守卫错误并被 effect 吞掉。插件保留原有的变通：把自身注入作用域作为 owner 传给服务原型上的 `register(owner, channel, handler)`。

0.1.7 的两点差异：`HostConnectionHandle` 仍然不声明这个 owner 重载（保留类型转换）；`rpcFetchHandler` 现在向 handler 多传一个 `peer` 参数，本插件的处理函数少声明一个参数，仍可赋值。

### 依赖解析树

0.1.5 时期的四项 `overrides`（`dsh-type-meta`、`dsh-compact`、`dsh-paths`、`dsh-user-interaction` → `dsh-brand`）本轮删除。这四个名字在 0.1.7 线上依然返回 404，但 0.1.7 的解析树也不再请求它们：`dsh-settings` 现在依赖 `@deepseek-ai/cosmokit`、`@deepseek-ai/dsh-config-editor`、`@deepseek-ai/cordis-plugin-loader`。别名属于「无请求即无效」的防御性配置，而 0.1.7 的 peer 范围（`~4.0.4` / `~3.18.4`）本身已经收窄。

## 已知缺口

1. **`plugin-check` 的 verdict 是 `warn` 而不是 `pass`**：唯一 warning 是 `not-in-hub`（本仓库未登记进 hub workshop catalog）。这与宿主版本无关——在 `v0.8.6-rc.3` 基线上跑同一个 checker 得到完全相同的 19 passed / 1 warned。CI 的 `plugin_check verdict is pass` 步骤在 fork 上会因此失败，需要上游把仓库收进 catalog，或由维护者决定该 warn 是否放行。
2. **`lib/` 产物已重建并保持确定性**（连续两次 `npm run build` 的 sha256 一致）；CI 的 `git diff --exit-code -- lib/` 应在提交后复核。
3. **锁文件按最小改写生成**：沿用 0.1.5 时期的既有条目，只移除 `@deepseek-ai/*` 子树并从 `package.json` 重新求解。实测结果是 50 个条目变化——31 个属于 dsh 树，19 个是 0.1.7 新引入的传递依赖（`js-yaml`、`ajv`、`semver`、`yaml`、`node-addon-*` 等，由 `dsh-settings@0.1.7` 的新依赖带来）。`undici`、`eventsource-parser`、`vitest`、`esbuild`、`typescript`、`zod`、`rolldown`、`postcss` 全部保持原版本，没有被顺带抬升。`npm ci` 在该锁上可复现安装，构建产物确定。
