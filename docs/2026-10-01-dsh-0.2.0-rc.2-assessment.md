# dsh 0.2.0-rc.2 适配评估（本分支）

> 本文记录 2026-10-01 起对 dsh `0.2.0` 宿主线的接缝核对与本次改动范围。基线是上游 main（已含 0.1.7 适配，包版本 `0.1.7-rc.1-v0.3`，发布在 npm `latest`）。上一轮（0.1.7）的记录见 [0.1.7-rc.1 适配评估](2026-09-24-dsh-0.1.7-rc.1-assessment.md)，那是历史快照，不是现行兼容说明。本分支是 fork 提回上游的 PR，**上游 CI 与发布结论以维护者为准，本文不替上游下结论**。

本次选择**只支持 0.2.0 线**，`0.1.7` 及更早的宿主由入口版本 guard 明确拒绝并给出升级命令。理由是两条宿主线的 `dsh-llm` 具名导出面与消息词表有别（见下），一份代码不承诺同时服务两条线。**注意：真正逼迫换线的不是自有 RPC 通道的注册方式**——那段代码在两条线上其实是同一份（见「关键决定 1」），起初把接缝写成「私有 `register` → 公开 `rpc.handle`」是本轮的一次误判，已由 CI 的真实启动检查纠正。

CI 的固定宿主同步抬到 `0.2.0-rc.2`：`.github/workflows/ci.yml` 的 `plugin-check` 与 `boot` 两个 job 的 pin 都改了；插件的解析树中 `dsh-*` 包一律切到 `0.2.0-rc.2`。

## 0.2.0 相对 0.1.7 的接缝变更

`@deepseek-ai/dsh-llm` 的具名导出面在两条宿主线之间是 **+2**：0.1.7 为 63 个名字，0.2.0 为 65 个，新增 `ACCOUNT_QUOTA_EXCEEDED_CODE` 与 `projectToolUpdates`，无删除。这意味着 `test/host-compat.mjs` Block A 的具名导入交集断言在新快照下照常通过；Block E 仍然守护「被拒绝的旧宿主面能完成 ESM 链接」。

`LlmAdapter` 在 0.2.0 多出 `prepareCall(provider, model, signal)` 方法，但带有默认实现，不需要子类覆盖。`LlmRuntime.registerAdapter` / `registerConfigurableProviders` / `registerModelDiscovery` 三个方法签名未变。设置接缝（volatile Config / `settings.configure({ auto: false })`）与消息词表（tool 角色消息直通、显式拒绝 `developer` / `tool-addition` / `tool-removal` / `deferLoading`）是 0.1.7 那轮引入的，本轮沿用。

### RPC 通道的公开 API 在 0.2.0 上仍不可用

`@deepseek-ai/dsh-client-connection` 在 0.2.0 把 `HostConnectionHandle.rpc: HostConnectionRpc` 写进了公开类型，其中 `handle(channel, handler)` 看着正是插件需要的注册入口。但它在运行期**依然是坏的**，原因与 0.1.7 完全相同：

```js
// dsh-client-connection@0.2.0-rc.2 lib/index.js
get rpc() {
  const owner = this.ctx           // ← connection 服务自身的 ctx
  return { handle: (channel, handler) => this.register(owner, channel, handler) }
}
register(owner, channel, handler) {
  ...
  return owner.effect(() => owner.webServer.register(route), ...)
}
```

`HostConnectionService` 只声明 `inject = ['credentials']`，Web 传输是挂在自己的 `ctx.inject(['webServer'], …)` 子作用域里的，所以服务自身的 `ctx` 上**没有** `webServer`。`owner.webServer` 于是触发 cordis 的 `cannot get property "webServer" without inject`，异常被 effect 吞掉，通道静默缺失，浏览器只能撞上 SPA fallback 的 405。

旁证：上游自己从不调用 `rpc.handle`。`deepseek-harness` 里唯一的用法是 `dsh-api-gateway` 的 `rpc.intercept('/api', matches, handler)`，那条路径走 `this.interceptors`，不碰 `webServer`——所以这个缺陷在 0.2.0 上没有被上游的任何测试或调用者暴露。RPC handler 在 0.2.0 上多接收第 4 个 `peer` 参数，本插件的处理函数少声明它，仍可赋值。

## 关键决定

**1. 自有 RPC 通道继续走 `connection.register(owner, channel, handler)`**：把自身注入作用域（那个**有** `webServer` 的 `cctx`）作为 owner 传进去，`register` 就能落地 `webServer.register(route)`。该方法在 0.1.7 与 0.2.0 上都存在于服务原型上（TypeScript 层是 `private`，故类型上需要一个 `as unknown as { register(...) }` 的形状声明——`private` 只是编译期约束，运行期方法可用）。

这次是本轮唯一一次「改错了再改回来」：最初的版本删掉 owner 变通、直接调 `connection.rpc.handle`，本地 typecheck/build/单测全绿，但**上游 CI 的 `boot` job 真实启动后报 `RPC channel /llm-newapi failed (HTTP 405)`**。本沙箱的 `/root/.dsh/profiles/web` 只读，无法在本地复现真实启动，所以这个错误只能由 CI 抓出来。结论：**类型声明和变更说明不能代替真实宿主验证**。

**2. peer 范围与最低版本 guard 同步抬到 `0.2.0-rc.1`**：peer 写作 `>=0.2.0-rc.1 <0.3.0`（不接受 0.1.x），`src/index.ts` 的 `MINIMUM_DSH_VERSION` 同步设为 `0.2.0-rc.1`，`test/host-compat.mjs` Block C 用这同一字符串生成断言正则。

**3. 被拒绝线 fixture 换到 0.1.7**：`REJECTED_SNAPSHOT_PATH` / `REJECTED_VERSION` 从 0.1.5 改为 0.1.7；`dsh-llm-0.1.7-rc.1.exports.json` 补上 `"version": "0.1.7-rc.2"` 并把 `0.1.7-rc.2` 加入 `surfaceSharedBy`，以匹配 Block C 的拒绝体取值。原 `dsh-llm-0.1.5.exports.json` 保留在仓库但不再被任何门禁引用。

**4. `test/smoke.mjs` 的 `FakeConnection` 保持不变**：它本就忠实复现了这条约束——`rpc.handle` 传入的是服务自身 `ctx`（无 `webServer`），只有显式传 owner 才能装成。既然生产代码维持 owner 变通，替身也维持原形；0.1.7 与 0.2.0 的运行期形状在这里是一致的。

## 与上轮 0.1.7 评估的差异

1. **本轮真正的接缝是「宿主线上移 + 导出面 +2」而非 RPC API 重塑**：0.1.7 那轮改的是 `settings.installSection` → `.volatile()` + `loader/volatile-update`（真实代码变更）；本轮的代码改动很小，主要是版本元数据、快照与文档。最初误判为「私有 `register` → 公开 `rpc.handle`」，已被 CI 的真实启动检查纠正。
2. **导出面差异只有 +2**：0.2.0 比 0.1.7 多 `ACCOUNT_QUOTA_EXCEEDED_CODE` 与 `projectToolUpdates`，无删除；0.1.7 那轮是 4 增 2 减。
3. **测试 fixture 新增一张（按宿主线）**：`dsh-llm-0.2.0-rc.2.exports.json`，语义仍是「以宿主线为单位」。
4. **锁文件改动量更小**：本轮净 -24 条（25 条移除、1 条新增），其中 9 个 dsh 内部包与 16 个传递依赖随 0.1.7 子树一起消失，非 dsh 外部依赖未换版本；0.1.7 那轮是 50 个条目变化（含 19 个新传递依赖）。
5. **peer 下限与开发 pin 首次分离**：0.1.7 时两者相同（同线只有一个可用版本）；0.2.0 的 pin 是 `rc.2`、下限是 `rc.1`，因为两者共享同一导出面。
6. **本轮由上游 CI 而不是本地验证兜底**：`boot` job 是本分支第一次真正跑起来的真实启动检查（PR #6 那条线上游还没有 CI），它抓出了本地环境无法复现的 405。
